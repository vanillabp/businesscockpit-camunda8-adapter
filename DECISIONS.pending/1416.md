The text to add:

---

Added on 2026-10-07, after story 1416.

The note of the start does not end the wait of point 3 above. On line 8.8 a process started by a call
activity still waits inside its listener job until the storage names its root, for up to
`workflow-visibility-timeout`. `workflowIdOf` could only spare the root itself this wait. Asked with
the module, the process of the job and the aggregate id, it returns a key. If that key is the job's
own process instance key, the instance is its own root. For a called process this gives nothing. To
find the root, the line class would need the bpmnProcessId of the root, and an 8.8 job does not carry
it. The line class would also need the election and the module id, and it has neither.

So this is not built. A called process, the one case this class is for, would still wait. Lines 8.9
and 8.10 read the root from the job and do not wait at all.
